Features

A detailed look at what Knot does today, verified against the codebase. Only SugarCube 2 has full language features; Harlowe, Chapbook, and Snowman are placeholder implementations with the build pipeline working. The current release is v2.1.0 — anything marked Unreleased is in the repository build but not yet in a Marketplace release.

Version-aware SugarCube 2 support

SugarCube has shipped breaking changes across its 2.x life — macros added, deprecated, and removed (2.37.0 alone removed six). Knot's macro catalog is a versioned union catalog: every macro that ever existed in SugarCube 2.x carries its lifecycle (added_in / deprecated_in / removed_in) plus per-era descriptions and argument signatures, sourced from the official docs, upgrade guides, release notes, and the 2.37.3 engine source.

Every user-facing feature resolves through the story's pinned format-version from StoryData:

  • Completions only offer macros that exist at your version — <<type>> and friends are hidden for stories pinned below their introduction, and macros removed in 2.37.0 are offered again for older stories.
  • Lifecycle diagnostics — sc-macro-removed (Error: removal version, replacement, downgrade guidance) and sc-macro-not-in-version (Warning: the version the macro was added in).
  • Hover and signature help resolve era-appropriate documentation, with tombstone notes for macros that don't exist at your version.
  • Special passages like StoryDisplayTitle (2.31.0) and the [init] tag (2.36.0) are only special on versions that have them.
  • Editing format-version triggers a full reindex — everything updates immediately.

Stories without a parseable version fail open to the latest known SugarCube — unusual metadata degrades to the full current surface, never to bogus diagnostics.

Structural understanding, not just regex

Unlike tooling that bolts regular expressions onto a text editor, Knot actually parses your project into passages and the links between them. This structural model lets it answer questions that pattern matching gets wrong:

  • "Where is this variable set?" — Knot tracks definitions across passages, not just mentions.
  • "Is this passage reachable from Start?" — a graph reachability check, not a string search. Static analysis can't see through variable-aliased navigation (<<goto $next>>), so you can mark entry passages with "reachable": true header metadata — the warning even offers a quickfix that writes it for you Unreleased.
  • "Which passages link here?" — reverse navigation through the link graph.
  • "Are there any orphan passages?" — passages nothing links to, flagged automatically.

This is the core design principle behind Knot: model the project the way Twine itself models it, and the editor can give you real help instead of approximate help.

Variable tracker

The Variable Tracking panel shows where every variable is set, read, and how it flows across passages. For SugarCube, variable tracking is JavaScript-aware via the oxc parser, so it understands:

  • <<set $x to 1>> — SugarCube macro syntax
  • <<run $x++>> — inline expressions
  • JavaScript inside <<script>> blocks
  • Variables passed through <<include>> and similar macros

This means Knot can warn you about uninitialized variables, unused variables, and variables that are read but never set — all in real time as you type. When JavaScript inside a passage has a syntax error, the parser recovers chunk-by-chunk so one broken block doesn't blind the rest of the file.

Embedded CSS linting

Twine projects embed CSS in passages more often than they keep it in separate files — and a single typo can make a browser silently drop an entire rule. Knot runs a real CSS parser over every stylesheet surface and reports:

  • Parse errors on [stylesheet] passages, <style> element bodies, and <<style>>/<<css>> blocks — including style="…" attribute values.
  • Unknown properties against a curated 500+ property registry (custom and vendor-prefixed names are always allowed) — flags colr-style typos.
  • Pseudo-class and pseudo-element typos — :hvoer, ::befor, the typo class browsers punish with total rule silence — plus a placement lint for pseudo-elements that aren't last in their compound selector.

Embedded HTML validation

Passages and StoryInterface files mix prose with markup, so Knot validates the HTML it finds there with tolerance matching the Twine engine's own:

  • Unclosed elements (Error), duplicate attributes and missing attribute values (Warning), and unterminated tags at passage end (Warning).
  • Attribute directive support — @attr="expr" / sc-eval:attr="expr" recognition with completions for the directive families, version-gated to SugarCube 2.21.0+ where they exist.
  • Deliberate silence on prose <, stray end tags, and literal regions (<nowiki>, {{{ }}}) — matching what the engine actually tolerates, so you're not spammed with non-errors.

StoryInterface passages get full semantic highlighting — tag names, attributes, entities, and delimiters — via the same token pipeline.

Story Map

An interactive graph visualization of your entire project. Nodes are passages, edges are links. The map is built on @xyflow/react with automatic layout via dagre.

  • Click any node to jump to that passage in the editor — including passages in closed files, at the correct line Unreleased.
  • The map updates in real time as you edit — no manual refresh.
  • Passage metadata (position, group, color) round-trips through the map; manual entry points render with their own green ring, corner marker, and tooltip Unreleased.
  • Special passages get distinct node colors; dead-end passages get a yellow double border; unreachable passages are grouped separately.

The Story Map is primarily for visualization and navigation at this time. Deeper structural editing from the map — dragging passages to reorganize, creating links visually — is on the roadmap.

The Knot IDE sidebar

Beside the editor, Knot installs a dedicated activity-bar panel (the Knot icon on the left edge of the window) with three views:

Passage Diagnostics

Live inspection of the passage under the cursor: links, variables, macros, and complexity metrics.

Variable Tracking

Where every variable is set and read, and how values propagate across passages.

Project Info

Workspace statistics: passage and word counts, format and version, IFID, graph health.

Incremental analysis

Knot doesn't re-parse your entire project on every keystroke. Only affected passages are re-parsed, and the graph is updated incrementally. This keeps large projects responsive even as they grow into hundreds of passages and thousands of links.

Integrated build pipeline

Knot's build pipeline is designed to "just work" with zero manual setup:

  1. Tweego is auto-downloaded on first build into the extension's global storage. You never need to install it yourself.
  2. Story formats are auto-downloaded based on your project's StoryData format and version. The format is cached per version in <globalStorage>/storyformats/<id>@<version>/.
  3. The workspace is the source directory — put all your .twee, .js, .css, and asset files directly in the workspace. Story formats live separately in the managed folder, so there's no risk of format.js getting bundled as a passage.
  4. The output filename is derived from StoryTitle — if your story is called "The Lost City", the build produces The_Lost_City.html. Falls back to index.html if no StoryTitle passage exists.
  5. Build stats are logged — every build prints Passages: N | Words: N to the Knot Build output channel.

Beyond the defaults, a knot.json file in the workspace root can override the story format and version and declare special passages explicitly.

Watch mode

Toggle auto-rebuild on save. When Watch is on, every save of a .tw, .twee, .js, or .css file triggers a rebuild in the background. This is the recommended workflow for active development: edit, save, refresh the browser.
